# Database-backed audit (v2.0)

This is the v2.0 workflow for new audits and existing `AUDIT.db` databases. The coordinator builds
and refines the source-linked proof graph; the controller prepares bounded assignments and saves
structured results. Existing v1.5 audit folders retain their legacy workflow until explicitly
imported. Software checks and a bounded live pilot passed; real-browser visual acceptance and
large-paper performance measurement remain outstanding. Completion never certifies mathematical truth.

Entry point: `python "<skill-root>/scripts/paper_audit.py" <command>`. It runs the generated
`scripts/paper_core/` bundle beside it. It never reads the legacy `proofcheck.py`, never looks up a
sibling skill, and works from a plain installed copy. Confirm the installation before relying on it:

    python "<skill-root>/scripts/paper_audit.py" version

That reports `core_version`, `storage_format`, `contract_version`, `contract`, `packet_version`,
`projection_version`, and a `bundle` block. `bundle.ok` must be `true`. A `false` or absent value
means the installed files no longer match their manifest; stop and report a damaged installation
instead of writing records with it.

## Command contract

Every command writes exactly one JSON object to stdout; diagnostics go to stderr. Parse stdout, do
not scrape stderr. Exit codes carry the meaning:

| Code | Meaning |
|---|---|
| 0 | Accepted, or the read succeeded |
| 2 | Invalid request or invalid data |
| 3 | Conflict; another writer advanced the record. Request a replacement packet and redo the edit |
| 4 | Incompatible schema or package |
| 5 | Source unavailable |
| 6 | Render or publication failure |

An incomplete mathematical assessment is a successful `status` query with `process_complete: false`
and exit 0. It is not a command failure and must never be reported as one.

A failing command includes `error: {code, message, records, ...}`. Report the code and inspect
`stored` on `work submit`: malformed or stale worker input may be retained for recovery without
changing the mathematical revision. A failed mathematical batch commits none of its included edits.

Pass `--run-id RUN` to every command in a session to record timing telemetry, then read it with
`telemetry summary DB --run-id RUN`. Timing receipts are observational; they measure commands, not
mathematical effort.

## Records and identity

The database is the single authority. There is no second master, no editable report source, and no
ledger file to hand-edit. Records are versioned and append-only: an accepted edit writes a new
version and never mutates an old one. Never open the SQLite file with another tool to change data.

Every edit batch names the packet it was authored against and the exact version it expected:

    {"contract_version": 3, "request_id": "<from ids --kind request>",
     "packet_id": "<from get>",
     "edits": [{"op": "create", "collection": "items", "id": "itm_...",
                "expected_version": null, "body": {...}}]}

`expected_version` is `null` for a create and the current version for an update. A stale value is a
conflict (exit 3), not a merge. Re-request the packet, reread the current record, and reauthor the
edit; do not retry the same batch.

Mint graph identifiers with `ids --kind COLLECTION --count N` and `ids --kind request`. Packet IDs
come from `get` or `work prepare`. Controller task IDs are derived, and accepted result IDs are
generated by the controller. Copy them; do not derive them from theorem numbering.

## Workflow

### 1. Create the database and capture source

    python "<skill-root>/scripts/paper_audit.py" init AUDIT.db --source-root "<paper-dir>" --title "<title>"
    python "<skill-root>/scripts/paper_audit.py" source capture AUDIT.db --files FILES.json

`FILES.json` is an array of paths relative to the registered root. Capture returns source revisions,
declaration and citation candidates, and its own limitations. A missing root or file is exit 5.
Candidates are parser output, not mathematical evidence.

Anchor the passages you will cite, through a packet:

    python "<skill-root>/scripts/paper_audit.py" source anchor AUDIT.db --request ANCHORS.json

Anchor requests are `{contract_version, request_id, packet_id, anchors: [{id, expected_version,
source_id, locator}]}`. A locator names either a label or a line range; the command extracts the
bytes, excerpt, and hash. Record branch, locator, and context decisions with `source review`.

### 2. Register the item graph

Use [graph-records.md](graph-records.md) for the complete closed body fields, allowed categories,
source-anchor requests, and a small source-linked graph example. This is coordinator authoring,
separate from the checker's structured response.

Request an author packet, then apply the structure batch:

    python "<skill-root>/scripts/paper_audit.py" get AUDIT.db --target papers:<paper-id> --mode author --out PACKET.json
    python "<skill-root>/scripts/paper_audit.py" apply AUDIT.db --batch BATCH.json

Register items with their statement and proof passages, scopes, one argument per written route,
groups for each meaningful inference, and one use per actual dependency. Record the use, not the
presence of a citation; several inputs may be required together. Keep routine algebra inside a
derivation rather than making a node for every source line. The coordinator reads the manuscript
and decides this structure. A script can detect a missing recorded target or establishing route;
it cannot discover a mathematical premise that was never registered.

Record source-versus-record observations separately with `compare AUDIT.db --packet ID --batch
OBSERVATIONS.json`, or include comparisons with checks in one controller response. Comparison is
source fidelity only and never mathematical support.

### 3. Register the audit and check it

For an audit with independent review, arrange genuine balanced calibration and record its reviewer
qualification using [database-qualification.md](database-qualification.md). That reference supplies
the complete receipt shape and a mechanical way to preserve actual worker bytes; it does not require
reading implementation code or starting a legacy audit. Record the qualification with:

    python "<skill-root>/scripts/paper_audit.py" qualification record AUDIT.db --receipt RECEIPT.json

Then register the audit through the authoring commands above. A `full` or `focused` audit must list exactly the three global tasks `global_consistency`,
`adversarial`, and `method_interface`, each with a `kind`, an `applicability` of `required` or
`not_applicable`, and a reason. Omitting one is an invalid batch.

Use [controller-workflow.md](controller-workflow.md) for the command sequence and exact response
fields, and [checker-protocol.md](checker-protocol.md) for mathematical work:

    python "<skill-root>/scripts/paper_audit.py" work list AUDIT.db --audit <audit-id>
    python "<skill-root>/scripts/paper_audit.py" work prepare AUDIT.db --audit <audit-id> --mode primary --focus items:<item-id> --out assignment
    python "<skill-root>/scripts/paper_audit.py" work submit AUDIT.db --submission SUBMISSION.json --response RESPONSE.json

Preparation selects one coherent sequence of context units, normally progressing from prerequisites
toward the target. The coordinator then dispatches the model. One response can save source fidelity,
individual applications, joint derivation, explicit coverage, and final composition together. These
remain distinct records without requiring a model call per record. Save useful partial reasoning or
drafts before yielding. Two supported applications do not establish their joint conclusion.

Read progress at any point:

    python "<skill-root>/scripts/paper_audit.py" status AUDIT.db --audit <audit-id>

`status` separates structural health, source limits, review coverage, mathematical assessments, and
the published revision. `work list` adds actionable tasks and coordinator diagnostics derived from
the same obligations; `progress` counts examined work, independently of whether outcomes are positive.
A recorded source issue appears in `source_limits` and blocks completion until resolved.

### 4. Independent review

Cut a blinded packet and dispatch it to a fresh context:

    python "<skill-root>/scripts/paper_audit.py" work prepare AUDIT.db --audit <audit-id> --mode independent --focus items:<item-id> --out independent-assignment

An independent packet carries source evidence and declared scope, and carries no checks, no primary
reasoning, and no assessment. Do not give the worker a database path, a working report, an unblinded
export, or the parent conversation. Submit its unchanged bytes:

    python "<skill-root>/scripts/paper_audit.py" work submit AUDIT.db --submission SUBMISSION.json --response RESPONSE.json

Give the independent worker only its worker packet and protocol, never the coordinator manifest,
which can contain task identities and primary context. The coordinator authors `SUBMISSION.json`
using the controller envelope, including `rebase_packet_id: null`; the worker authors `RESPONSE.json`.
The existing direct `get` / `review submit` path remains available for ordinary review packets.
A response whose
judgments point at source anchors rather than canonical targets is preserved as `needs_revision`
until the coordinator maps it with `review map`. Mapping cannot change the worker's outcome,
reasoning, or evidence. The original bytes are retained permanently.

Then prepare reconciliation and submit the coordinator's authored batch through the controller:

    python "<skill-root>/scripts/paper_audit.py" work prepare AUDIT.db --audit <audit-id> --mode reconcile --focus items:<item-id> --out reconciliation
    python "<skill-root>/scripts/paper_audit.py" work submit AUDIT.db --submission SUBMISSION.json --response RECONCILE.json

Each reconciliation pins the exact primary and independent check versions it compared. Both original
judgments survive. Unresolved disagreement stays visible rather than resolving to green.

### 5. Report and release

    python "<skill-root>/scripts/paper_audit.py" checkpoint AUDIT.db --out report.html
    python "<skill-root>/scripts/paper_audit.py" validate AUDIT.db
    python "<skill-root>/scripts/paper_audit.py" release AUDIT.db --audit <audit-id> --out release-dir

`checkpoint` builds an honest working report; if the build fails it retains the prior HTML byte for
byte and reports exit 6 with the prior output retained. `validate` checks shapes, references,
bindings, coverage intervals, and projection inputs; it certifies nothing mathematical. `release`
requires process completion and then writes an immutable directory with the report, export, and
receipt; a blocked release is exit 2 with `RELEASE_BLOCKED` and creates no directory.

Completion means the audit process finished, not that the paper is correct. A completed audit may
report gaps, refutations, or adjudicated inconclusive findings. It may not hide undone work, stale
obligations, or missing independent review.

`export AUDIT.db --out snapshot.json` writes a mathematical contract-3 snapshot. It is not a recovery
archive of packets, commits, or retained malformed responses. Use `backup AUDIT.db --out copy.db`
for complete SQLite recovery. `changes AUDIT.db --since REV` lists what changed
after a revision with the affected checks and the reason each was affected.

## Legacy audits and overview databases

    python "<skill-root>/scripts/paper_audit.py" import-legacy <audit-folder> --db NEW.db --map MAPPING.json

Import creates a new database only. It preserves the original artifacts, writes an ID mapping, and
marks the imported checks as historical. It is refused on a database that already holds the import.
Never run new-format data through the legacy ledger validator, and never point the legacy runtime at
a new-format database.

New databases use storage format 3, record contract 3, and packet/projection version 2. Existing
native storage format 2 is readable but must be explicitly upgraded before writing:

    python "<skill-root>/scripts/paper_audit.py" migrate AUDIT.db --backup pre-controller.db

Migration preserves mathematical revisions and historical packet-1 bytes. It does not recheck a proof.
An archify overview database instead uses `format: archify-paper-database-1` and `schema_version: 2`;
those identifiers are unrelated to native storage format 2. It is reported as exit 4 `INCOMPATIBLE`
until explicitly upgraded with `migrate-overview DB --backup BACKUP`, which preserves item, use, and
anchor identity together with recorded observations. `attach DB --report report.html` registers a
proofcheck report on a compatible overview database without creating a second master.

## Boundaries

- Tooling owns hashes, source partitions, excerpts, bindings, graphs, progress, and generated views.
  It never owns a mathematical judgment.
- The checker owns normalization, mathematical judgments, failure evidence, and issue
  classification.
- Do not infer correctness from a green node. Colors are derived from recorded evidence and carry
  their qualifications.
- A changed caption or unrelated progress need not invalidate local mathematics. Use the controller's
  task-specific freshness check for an explicit rebase; changed consumed mathematics requires renewed
  reasoning. Exact source relocation still follows the existing source-review/reuse rules.
- Report software checks, browser inspection, and mathematical evaluation separately.
